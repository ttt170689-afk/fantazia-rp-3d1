## Как подключить лаунчер

В рабочей копии TEMKALAUCHER, содержащей указанный commit:

```sh
git apply --check /путь/launcher-site-login.patch
git apply /путь/launcher-site-login.patch
npm ci
npm test
npm run build
```

Патч включает компонент `FantaziaSiteLogin`, клиентский запрос, тесты, обновлённый `GameProperties`, а также зеркала `native-bundle`, их контрольные суммы и allowlist `restore-native.mjs`. Поэтому штатное восстановление runtime не стирает новую кнопку. Не применять патч с игнорированием конфликтов к другой версии — сначала сверить изменения.

Новую версию лаунчера выпускай обычным процессом проекта с увеличением номера версии. Никакие серверные секреты в `.env` лаунчера или в `VITE_*` не добавлять.

Кнопка находится в **Fantazia → Свойства → Бета-тест → Код входа на сайт**. Она доступна подтверждённому онлайн-профилю; решение о выдаче всегда принимает сервер, включая проверку роли владельца. Код очищается при смене аккаунта/закрытии окна, не сохраняется в localStorage, URL или журнале. Копирование — только по нажатию пользователя.

## Как обновить сайт

Использовать текущую защищённую версию Fantazia из main, а не старые v45-архивы до введения закрытого доступа. Изменения этой задачи: `server/closed-beta.cjs`, `server/closed-runtime.cjs`, новый `server/launcher-login.cjs`, миграция `backend/launcher-login.sql` и тесты.

Миграция MAIN уже применена. На Render используется СУЩЕСТВУЮЩИЙ `FANTAZIA_RUNTIME_SECRET` — менять, раскрывать или пересылать его не нужно. После проверки/объединения изменений опубликовать сайт обычным процессом Render. Старые cookies и парольный вход MAIN остаются совместимыми. Email-OTP больше не рекламируется как код лаунчера; его старые серверные маршруты не обходят проверки допуска.

## Протокол

1. Лаунчер использует существующий MAIN-клиент `withDevSession` исключительно как уже имеющийся механизм свежего MAIN access token и контроля смены аккаунта. Никакого Dev Auth входа/нового пользователя/передачи refresh token нет.
2. `POST https://fantazia-rp-3d1.onrender.com/closed/launcher-code`:
   - `Authorization: Bearer <MAIN access token>`; тело `{}`; `credentials: omit`.
   - Сервер заново проверяет `/auth/v1/user`, подтверждённую почту, `my_profile`, одобрение Fantazia либо `fantazia_owner_status`. Переданные клиентом ID/роли не принимаются.
   - Ответ: `{ok:true, code:"FZ-XXXX-XXXX-XXXX-XXXX", expires_at:"...", expires_in:120}`. Это пример формата, не действующий код.
   - CORS разрешён только на этом bearer-маршруте, без credentials. Остальные HTTP/API/Socket.IO ограничения не ослаблены.
3. Форма `/closed/login` отправляет `POST /closed/launcher-login`, поле `code`. Нужен same-origin Origin; код не передаётся в URL.
4. Код — 80 случайных бит; в БД хранится HMAC кода, MAIN user ID и зашифрованный access token. Срок 120 секунд. Действует только последний выданный код пользователя. Повторная выдача при действующей записи — не чаще раза в 30 секунд; также есть IP-лимиты выдачи/погашения.
5. Погашение — атомарный SQL DELETE, затем проверка MAIN-сессии/допуска без обычного 10-секундного кеша и сравнение UID. Одновременные запросы не могут использовать один код дважды. Если проверка после погашения не прошла, нужен новый код.
6. Сайт выдаёт существующий зашифрованный `HttpOnly; Secure; SameSite=Strict` cookie. Никакой альтернативной авторизации по коду в API/Socket.IO нет: дальше работают прежние проверки MAIN и закрытого допуска.

**Срок веб-сессии:** refresh token лаунчера не копируется. Когда переданный MAIN access token истечёт, потребуется новый код из лаунчера. Это намеренно не продлевает токен и не вмешивается в обновление MAIN-сессии лаунчера. Отзыв допуска проверяется существующими HTTP/socket-механизмами.
